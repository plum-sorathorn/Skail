# AutoConduck v0.4.x — Session-Scoped Harness-Supervised Execution

**Status:** Proposed  
**Target version:** v0.4.x (next minor release after 0.3.5)  
**Decision type:** Architecture / execution-model ADR

## Executive Summary

AutoConduck’s current dynamic orchestration has two structural limitations: its LangGraph DAG performs only brief, read-only reconnaissance, and its resulting memo is injected into one harness agent that then executes implementation linearly. This loses the harness’s native tools, execution loop, and—where available—native parallel or multi-agent capabilities.

v0.4.x promotes AutoConduck from a per-turn planning DAG into a **session-scoped supervisor**. The harness remains the sole execution authority: it uses its own tools and, when capable, its own native fan-out mechanisms. AutoConduck provides a durable live plan, emits executable phase contracts with explicit dependency and parallelism hints, observes subsequent harness turns, and asynchronously mutates unfinished work between turns. It never attempts to push control into an external harness, does not perform the real implementation through internal writer agents, and does not introduce a synchronous “run one phase, wait for harness, resume graph” puppet protocol.

The key boundary is:

> **AutoConduck proposes phases, dependencies, verification conditions, and parallelism. The harness executes them using its own native capabilities.**

---

## 1. Problem Statement

The existing orchestration path is valuable for planning and reconnaissance, but it is not an execution system:

1. AutoConduck builds a fresh DAG on each eligible turn.
2. Its subagents make single LiteLLM completions as read-only analysts.
3. The synthesizer turns findings into a markdown handoff.
4. AutoConduck injects that handoff into the harness message stream.
5. One external harness agent performs actual implementation with its own tools.

This means the current DAG does not gain the practical benefits users expect from multi-agent execution:

- Internal subagents do not use the harness’s filesystem, shell, browser, test, or editing tools.
- Internal subagents do not make changes.
- Internal subagents do not verify implementation results.
- The real work proceeds after orchestration, through one harness-driven execution stream.
- The plan disappears as a first-class artifact after the handoff and is rebuilt rather than evolved across turns.

The v0.4.x design addresses this without violating the provider architecture. Harnesses call AutoConduck as an LLM provider; AutoConduck cannot remotely command a harness to create workers, invoke tools, or resume a suspended workflow. Therefore, fan-out must be expressed as an executable request **inside the harness-visible handoff**, not implemented as an AutoConduck-owned worker pool.

## 2. Current Architecture Summary

### 2.1 Request and routing flow

The current verified flow is:

1. Claude Code, OpenCode, Pi, or another configured harness sends a turn to AutoConduck through an OpenAI- or Anthropic-compatible endpoint, commonly `/v1/chat/completions`.
2. `server/turn_guard.py` synchronously classifies the turn:
   - Active healthy tool loop: `DIRECT_ACTIVE_TIER`.
   - Genuine stagnation—three or more identical consecutive calls or two or more consecutive errors: `ESCALATE_SLM`.
   - Plain turn: `SLM_PLAN`.
3. `server/server_router.py` decides whether a pseudo-model request should enter slow orchestration. If it is not an active tool loop, it may call `orchestrator.run()`.
4. `orchestrator/runner.py::run_dynamic_orchestration()` constructs and runs a LangGraph DAG through `DynamicGraphRunner`.
5. `orchestrator/dynamic_factory.py` creates:
   - Optional RAG work.
   - One subagent node per `ExecutionPlan.subtasks`.
   - Dependency wiring from `depends_on`.
   - A synthesizer node that calls `format_execution_handoff()`.
6. `orchestrator/subagents.py::run_subagent()` performs one LiteLLM completion per subtask.

### 2.2 Current subagent boundary

Current subagents are explicitly read-only analysts. Their prompts begin with language equivalent to:

> “ROLE: You are a read-only file analyst. You do not propose fixes or write code.”

Although `SubTaskSpec.role` can contain values such as `recon`, `read`, `edit`, `verify`, `bash`, or `reasoning`, current behavior is effectively read/analysis only:

- No harness-native tools are called.
- No filesystem edits are made.
- No tests are run through the harness.
- No implementation is performed internally.
- No internal worker can independently complete a coding phase.

### 2.3 Current handoff boundary

`orchestrator/handoff.py::format_execution_handoff()` aggregates analyst results into a markdown “Implementation Plan & Verified Context” handoff. The server injects it back into the external harness’s own conversation as a user message, with an instruction to execute it using the harness’s available tools.

The harness is therefore the actual executor. Today, AutoConduck is accurately characterized as:

> **Reconnaissance followed by a memo to one harness agent.**

### 2.4 Existing session adaptation foundation

The repository already contains the beginnings of session-aware adaptation:

- `server/server_router.py::_get_session_key()` derives a session key from `x-session-id`, `x-thread-id`, or a hash of initial user content.
- `server/server_router.py::_session_replan_state` stores in-memory per-session state.
- `server/server_router.py::_run_async_slm_heartbeat()` asynchronously evaluates a session trajectory and may set `replan_pending` plus `escalation_plan`.
- `routing/slm_planner.py` defines:
  - `ExecutionPlan`
  - `SubTaskSpec`
  - `evaluate_session_trajectory()`
  - `evaluate_session_trajectory_async()`
  - `EscalationVerdict`

The v0.4.x design extends this foundation from “escalate to SLOW” into “evolve the remaining session plan.”

## 3. Core Design Decision: The Harness Owns Fan-Out

### Decision

AutoConduck will not implement the real work through internal writer, shell, or verifier subagents. Instead, it will issue a harness-visible, structured execution contract that describes:

- phases of work;
- dependencies between phases;
- independently executable work;
- suggested parallel groups;
- verification or post-conditions;
- phase completion ledger;
- remaining work and terminal criteria.

A capable harness may use this contract to invoke native subagents, parallel worktrees, task tools, tool loops, or other execution mechanisms. A harness without native fan-out executes the same phases sequentially.

### Why this is the correct boundary

#### AutoConduck cannot control an external harness

AutoConduck is configured as an LLM provider. The harness owns the agent loop, tools, tool-call scheduling, filesystem access, terminal execution, and any native delegation features. AutoConduck receives requests from the harness; it does not own an RPC channel through which it can instruct the harness runtime to spawn or coordinate workers.

Any design that assumes AutoConduck can “tell Claude Code/OpenCode/Pi to fan out now” through a private control plane is architecturally false unless each harness implements such a control plane. v0.4.x will not create harness-specific orchestration protocols.

#### The harness has the real execution capabilities

The external harness already has the operational context AutoConduck lacks:

- authenticated tool access;
- repository state at the time of execution;
- shell and test access;
- tool outputs and failures;
- user-visible progress and approval flow;
- native support for subagents or parallel tasks, where available.

A worker operating inside AutoConduck would either be crippled by design or would require duplicating these capabilities, permissions, safety controls, and state-transfer mechanisms. That duplication would be slower, less reliable, and contrary to AutoConduck’s local zero-overhead routing role.

#### AutoConduck’s differentiated role is supervision

AutoConduck can provide value without owning implementation:

- select planning and reasoning models;
- create a coherent session-level execution plan;
- identify independent work;
- encode verification requirements;
- observe the harness trajectory;
- asynchronously determine whether remaining phases remain valid;
- reduce unnecessary work by skipping obsolete phases;
- append follow-up work when evidence reveals a gap;
- issue a terminal decision only when post-conditions are satisfied.

This is a supervision and adaptation role, not a tool-execution role.

### Reconciliation with current internal subagents

Read-only internal subagent analysis may remain as an optional, bounded reconnaissance service. It is useful when a planning model needs parallel codebase inspection before it can form a good harness-facing plan.

However:

- Internal subagent output is advisory context only.
- Internal subagents are not the implementation critical path.
- Internal `edit`, `bash`, and `verify` role labels must not imply autonomous implementation authority.
- A phase marked parallel in the handoff is intended for the harness to execute in parallel, not for AutoConduck to silently create implementation workers.
- The plan must remain useful when internal reconnaissance is unavailable, disabled, or fails.

### Parallelism contract

AutoConduck emits two related concepts:

- `parallel_group`: a named group of phases that are safe to begin concurrently once their dependencies are met.
- `parallel_to`: an explicit per-phase list of phase identifiers that may execute concurrently with this phase.

The contract is advisory but normative in meaning:

- A parallel-capable harness should fan out work within a ready `parallel_group`, subject to its own safety, tool, and repository-concurrency policies.
- A sequential harness must preserve dependencies and may execute ready phases one at a time.
- A harness must never infer that phases are parallel merely because they appear adjacent in the handoff.
- AutoConduck must only mark phases parallel where their scopes and post-conditions do not require serialized repository mutation.

The resulting degradation model is intentional:

| Harness capability | Behavior |
|---|---|
| Native parallel/multi-agent execution | Execute independent ready phases concurrently using native capabilities. |
| Single-agent tool loop | Execute the same ready phases sequentially in dependency order. |
| No tool access | Receive the plan as advice; no claim of verified completion is made. |

## 4. Session-Scoped Live Execution Plan

### 4.1 Plan lifecycle

`ExecutionPlan` becomes a durable, session-scoped artifact rather than an ephemeral input to a newly rebuilt DAG on every turn.

A session has one active plan revision at a time. That plan is created when slow planning is justified and then evolves across turns until it reaches a terminal state.

The plan lifecycle is:

```text
created
  -> active
  -> mutated zero or more times
  -> terminal: completed | abandoned | superseded | expired
```

The initial plan may be assembled using current planner and optional read-only reconnaissance behavior. Subsequent session turns must preferentially use the active plan plus its ledger rather than independently rebuilding the work graph.

### 4.2 Phase model

The durable plan is composed of ordered but dependency-aware phases.

Each phase has at minimum:

```json
{
  "id": "phase-02",
  "goal": "Add request validation for malformed provider payloads.",
  "dependencies": ["phase-01"],
  "parallel_group": null,
  "parallel_to": [],
  "scope": [
    "server/messages_api.py",
    "tests/test_messages_api.py"
  ],
  "execution_mode": "harness",
  "post_condition": "Malformed payloads return the documented client error and valid payload behavior remains unchanged.",
  "verify": [
    {
      "kind": "test",
      "command_hint": "python -m pytest tests/test_messages_api.py -q",
      "success_condition": "Targeted tests pass."
    }
  ],
  "status": "pending"
}
```

The minimum semantic fields are:

| Field | Meaning |
|---|---|
| `id` | Stable phase identifier within the plan lineage. |
| `goal` | The concrete outcome the harness should achieve. |
| `dependencies` | Phase IDs that must be completed or explicitly skipped before this phase is ready. |
| `parallel_group` | Optional group name for independent work that may be fanned out by the harness. |
| `parallel_to` | Explicit phase IDs that may execute concurrently with this phase when dependencies are satisfied. |
| `scope` | Expected files, modules, tests, or operational area. This is guidance, not a write permission boundary. |
| `execution_mode` | Always `harness` for implementation phases in v0.4.x. Optional reconnaissance phases may be `autoconduck_recon`. |
| `post_condition` | Observable desired state after the phase. |
| `verify` | Concrete evidence the harness should obtain when feasible. |
| `status` | Current lifecycle state. |

### 4.3 Phase statuses

The canonical v0.4.x phase statuses are:

| Status | Meaning |
|---|---|
| `proposed` | Present in a newly generated or revised plan but not yet issued to the harness. |
| `pending` | Issued and eligible to become ready when dependencies resolve. |
| `ready` | Dependencies are resolved; the harness may execute it. |
| `running` | Harness trajectory indicates active work on this phase, but completion is not yet evidenced. |
| `completed` | Required post-condition and available evidence indicate completion. |
| `blocked` | The harness trajectory or explicit failure indicates that progress cannot continue without intervention. |
| `skipped` | No longer necessary; the skip reason is recorded. |
| `replaced` | Superseded by one or more replacement phases; replacement IDs are recorded. |
| `failed` | Attempted but not completed; follow-up or escalation is required. |
| `terminal` | Administrative final marker for a terminal plan only; phases themselves normally use `completed`, `skipped`, or `replaced`. |

`ready` may be derived at handoff time rather than persisted independently, but its semantics must be stable: a phase is ready only when all dependencies are `completed` or intentionally `skipped`.

### 4.4 Allowed heartbeat mutations

The asynchronous supervisor can mutate only unfinished work. It must preserve the immutable history of completed, skipped, replaced, and failed phases.

Allowed actions are:

1. **Keep**  
   Retain the remaining phase unchanged.

2. **Adjust**  
   Modify the goal, scope guidance, verification instructions, or parallelism metadata of an unfinished phase while retaining its identity and traceability.

3. **Skip**  
   Mark an unfinished phase `skipped` because available evidence shows it is unnecessary, already satisfied, or rendered obsolete by another change.

4. **Replace**  
   Mark a pending or blocked phase `replaced` and add explicit replacement phases. The old phase remains visible in the ledger with a reason and replacement IDs.

5. **Append**  
   Add a new phase after discovering unmet requirements, regression risk, required verification, or implementation work absent from the original plan.

6. **END**  
   Mark the session plan terminal only after all required post-conditions are satisfied or a documented non-completion terminal policy is selected.

The heartbeat must not retroactively rewrite completed work or erase phase history.

### 4.5 Last phase means end of execution

The final phase is not “synthesizer ran.” It is a phase with terminal post-conditions, normally verification and completion review.

A typical plan ends with an explicit final phase:

```json
{
  "id": "phase-99",
  "goal": "Verify all required behavior and determine whether the requested task is complete.",
  "dependencies": ["phase-01", "phase-02", "phase-03"],
  "parallel_group": null,
  "parallel_to": [],
  "execution_mode": "harness",
  "post_condition": "All requested changes are present, relevant verification passes, and no unresolved requested work remains.",
  "verify": [
    {
      "kind": "test",
      "command_hint": "python -m pytest",
      "success_condition": "Relevant test suite passes, or any pre-existing failure is explicitly identified."
    },
    {
      "kind": "review",
      "success_condition": "The harness reports no unresolved requested requirement."
    }
  ],
  "status": "pending"
}
```

The SLM may issue `END` early only if it has evidence that all remaining phase post-conditions are already satisfied. It may not end merely because the harness has taken many turns, touched many files, or emitted a plausible summary.

## 5. Harness Handoff Contract

### 5.1 Design requirements

The handoff contract must be:

- protocol-agnostic;
- readable by a human and a language model;
- parseable and versioned;
- usable by Claude Code, OpenCode, Pi, and future harnesses;
- safe for sequential harnesses;
- explicit about advisory parallelism;
- capable of carrying the accumulated phase ledger across turns.

It must not require a harness-specific control channel or a new provider API extension.

### 5.2 Canonical handoff envelope

`orchestrator/handoff.py::format_execution_handoff()` will evolve from a prose-only implementation memo into a stable execution envelope. The response remains injected into the harness message stream using the existing compatible server paths.

The canonical payload is a tight markdown wrapper containing a JSON contract:

```markdown
[AutoConduck Session Execution Contract]
schema_version: "0.4"
session_id: "<opaque session key or redacted session reference>"
plan_id: "<stable plan id>"
plan_revision: 4
decision: "continue"
decision_reason: "Phase phase-02 is complete; phase-03 remains required."
execution_authority: "harness"

The harness is the executor. Use your native tools and, when available, native worker or subagent fan-out. `parallel_group` and `parallel_to` are safe-to-parallelize hints, not a requirement. Preserve dependency order and verify each phase before reporting it complete.

```json
{
  "schema_version": "0.4",
  "plan_id": "plan_01J...",
  "plan_revision": 4,
  "decision": {
    "action": "continue",
    "reason": "The implementation phase is evidenced as complete; verification remains."
  },
  "execution_authority": "harness",
  "phases": [
    {
      "id": "phase-01",
      "goal": "Inspect the existing request-validation path and identify the minimal change.",
      "dependencies": [],
      "parallel_group": "recon",
      "parallel_to": ["phase-02"],
      "scope": ["server/messages_api.py", "tests/test_messages_api.py"],
      "execution_mode": "harness",
      "post_condition": "The implementation location and existing test conventions are identified.",
      "verify": [
        {
          "kind": "inspection",
          "success_condition": "Relevant behavior and tests are identified before editing."
        }
      ],
      "status": "completed",
      "evidence": [
        "Harness inspected server/messages_api.py and tests/test_messages_api.py."
      ]
    },
    {
      "id": "phase-02",
      "goal": "Add the minimal validation behavior and focused regression tests.",
      "dependencies": ["phase-01"],
      "parallel_group": null,
      "parallel_to": [],
      "scope": ["server/messages_api.py", "tests/test_messages_api.py"],
      "execution_mode": "harness",
      "post_condition": "Malformed payloads are rejected according to the documented API behavior without changing valid request behavior.",
      "verify": [
        {
          "kind": "test",
          "command_hint": "python -m pytest tests/test_messages_api.py -q",
          "success_condition": "Focused tests pass."
        }
      ],
      "status": "ready",
      "evidence": []
    },
    {
      "id": "phase-03",
      "goal": "Run final relevant verification and confirm completion.",
      "dependencies": ["phase-02"],
      "parallel_group": null,
      "parallel_to": [],
      "scope": ["tests/test_messages_api.py"],
      "execution_mode": "harness",
      "post_condition": "The requested behavior is complete and verification evidence is available.",
      "verify": [
        {
          "kind": "test",
          "command_hint": "python -m pytest tests/test_messages_api.py -q",
          "success_condition": "Relevant tests pass."
        },
        {
          "kind": "review",
          "success_condition": "No requested requirement remains unresolved."
        }
      ],
      "status": "pending",
      "evidence": []
    }
  ],
  "ledger": {
    "completed_phase_ids": ["phase-01"],
    "skipped_phase_ids": [],
    "replaced_phase_ids": [],
    "blocked_phase_ids": [],
    "current_ready_phase_ids": ["phase-02"],
    "last_harness_observation": {
      "turn_id": "<opaque turn reference>",
      "summary": "The harness inspected the implementation and test locations."
    }
  }
}
```

Execute the ready phases. If your runtime supports native delegation, phases in the same ready parallel group may be delegated concurrently. After executing, report concrete evidence: files changed, commands run, test results, unresolved blockers, and any deviation from the phase contract.
```

### 5.3 Handoff decisions

The top-level `decision.action` is one of:

| Action | Meaning |
|---|---|
| `continue` | Execute the currently ready phases. |
| `revise` | The plan changed; execute the newly ready replacement or appended phases. |
| `verify` | Implementation appears complete; obtain required final evidence. |
| `end` | All post-conditions are satisfied; no further requested execution is planned. |
| `blocked` | The supervisor cannot safely propose further execution without user or harness resolution. |

The `end` action is an instruction to stop pursuing the current task plan, not a mechanism to terminate the harness process or conversation.

### 5.4 Ledger semantics

The ledger is the session’s compact evidence record. It exists so a later plan revision can distinguish:

- work that is complete;
- work that was intentionally skipped;
- work that has been replaced;
- work currently blocked;
- phases whose completion is inferred but not strongly verified;
- tests or commands that have already been run;
- observed failures that must not be rediscovered repeatedly.

The ledger must be included in every supervisor-generated handoff after the initial plan. It must not claim completion solely because a phase was issued to the harness.

### 5.5 Backward-compatible rendering

The JSON contract is the canonical machine-readable content. A concise explanatory markdown summary remains required because existing harnesses consume ordinary user-message text rather than a dedicated execution API.

Handoff formatting must remain resilient:

- If structured serialization fails, emit a safe prose summary of the current plan and direct dispatch.
- If an old client sees the new block, it should still be able to execute the prose instructions.
- A schema version is mandatory for all structured handoffs.
- Unknown fields are ignored by consumers; unknown schema major versions are rendered as prose rather than trusted as executable structure.

## 6. Asynchronous Replanning and Heartbeat

### 6.1 Promotion of the existing heartbeat

`server/server_router.py::_run_async_slm_heartbeat()` currently supports asynchronous trajectory evaluation and can mark a session for replan or escalation. In v0.4.x, it becomes the session supervisor’s mutation engine.

Its responsibility changes from:

> “Should this session escalate to SLOW with a suggested plan?”

to:

> “Given the active session plan, phase ledger, and observed harness trajectory, which unfinished phases should remain, change, disappear, be replaced, be appended, or be terminally ended?”

The heartbeat remains asynchronous and must not block the request routing hot path or tool-loop guard.

### 6.2 Inputs

The heartbeat evaluates a bounded session snapshot:

- active plan ID and revision;
- phase definitions and statuses;
- compact phase ledger;
- recent harness-visible messages and assistant/tool trajectory already available to the server;
- recent tool success/failure signals where present in provider traffic;
- prior mutation reason and timestamp;
- optional current task constraints;
- current plan confidence and routing metadata.

It must use bounded context. It must not retain or resend an unbounded transcript on every turn.

### 6.3 Mutation output

The planner must return a structured mutation rather than only a replacement `ExecutionPlan`.

Conceptually:

```json
{
  "schema_version": "0.4",
  "plan_id": "plan_01J...",
  "base_revision": 4,
  "action": "skip",
  "reason": "The harness already implemented and tested the behavior covered by phase-03.",
  "mutations": [
    {
      "op": "set_status",
      "phase_id": "phase-03",
      "status": "skipped",
      "reason": "Post-condition is already evidenced by completed phase-02 verification."
    }
  ],
  "terminal_decision": null
}
```

Supported mutation operations should be deliberately small:

- `set_status`
- `adjust_phase`
- `replace_phase`
- `append_phase`
- `set_terminal_decision`

A mutation must target one base plan revision. The server applies it only if the active plan still has that revision or can safely reconcile it under an explicit compare-and-swap policy.

### 6.4 Turn ordering and consistency

The heartbeat runs between turns and cannot take control of the harness’s current in-flight tool loop.

The ordering contract is:

1. A request arrives and is classified normally.
2. Active healthy tool loops remain direct-dispatched by `Turn Guard`.
3. The server records the relevant trajectory observation in session state.
4. The asynchronous heartbeat may evaluate that state after the response path has continued.
5. If it produces a valid mutation for the active revision, the server atomically creates the next plan revision.
6. The next eligible planner-context injection reads the latest committed plan revision and emits the updated phase block.
7. No already-sent handoff is retroactively changed.

This is intentionally eventual, not synchronous. A harness may complete work based on an older phase revision before it receives a newer revision. The next heartbeat must reconcile that evidence rather than treating it as a protocol violation.

### 6.5 No wheel-taking behavior

The heartbeat is advisory supervision. It must not:

- invoke harness tools;
- spawn implementation agents;
- write files;
- synchronously pause the harness after every phase;
- issue a provider-level command that assumes the harness obeys;
- interfere with a healthy active tool loop.

It only updates the plan that will be supplied on a later eligible turn.

### 6.6 Mutation application safety

A heartbeat mutation is applied only when all are true:

- the session still exists;
- the target plan ID matches the session’s active plan;
- the base revision is current, or the mutation can be safely rebased using immutable ledger history;
- the structured result validates against the plan schema;
- the mutation preserves completed-phase history;
- the mutation does not introduce dependency cycles;
- phase IDs remain unique;
- terminal decisions satisfy terminal policy.

If any condition fails, AutoConduck records a diagnostic-safe fallback state and continues direct dispatch. It must not return a 500 or corrupt the active plan.

## 7. End-of-Session Is a First-Class Decision

### 7.1 Terminal decision model

Completion is not inferred from:

- the synthesizer completing;
- the original plan containing no more prose bullets;
- a fixed number of turns;
- a file-count threshold;
- a tool-loop count;
- a model asserting “done” without evidence.

A session plan is terminal only when the supervisor emits one of:

| Terminal state | Meaning |
|---|---|
| `completed` | Required post-conditions are satisfied and available verification evidence supports completion. |
| `abandoned` | Execution cannot continue without an external decision, permission, credential, or user clarification. |
| `superseded` | A new explicit task or plan replaces the current one. |
| `expired` | Session state is no longer available or valid; no completion claim is made. |

The normal successful path is `completed`.

### 7.2 Completion evaluation

Before `END`, the supervisor evaluates:

- whether every required phase is `completed`, `skipped` with valid rationale, or `replaced` by completed replacements;
- whether final verification phases have evidence;
- whether the user’s original requested outcomes are covered;
- whether the harness reported unresolved errors, failed tests, or blockers;
- whether a later harness action invalidated previously accepted evidence.

If implementation is likely complete but evidence is missing, the supervisor must issue or retain a `verify` phase rather than end the plan.

If verification fails or reveals missing work, it must append or replace with a focused follow-up phase.

### 7.3 Terminal handoff

A successful terminal handoff must be concise and explicit:

```markdown
[AutoConduck Session Execution Contract]
decision: "end"
reason: "All required post-conditions are evidenced; final verification passed."
execution_authority: "harness"

No further phases are planned for this task. Preserve the recorded verification evidence in your final response. If you detect an unresolved failure or unmet requested requirement, continue execution and report the contradiction; the next session heartbeat may reopen the plan.
```

This does not suppress the harness’s final user-facing summary. It tells the harness that AutoConduck has no additional work to inject.

## 8. Concrete File-by-File Change Plan

All changes must remain surgical and preserve the repository’s fail-soft behavior.

### 8.1 `routing/slm_planner.py`

#### Changes

- Extend `ExecutionPlan` into a versioned, session-capable plan representation.
- Add durable plan identity and revision fields:
  - `schema_version`
  - `plan_id`
  - `revision`
  - `session_status`
  - `phases`
  - `ledger`
  - `terminal_decision`
- Evolve or adapt `SubTaskSpec` into a phase-capable model with:
  - `dependencies` or compatibility mapping from `depends_on`
  - `parallel_group`
  - `parallel_to`
  - `post_condition`
  - `verify`
  - `status`
  - `execution_mode`
  - phase evidence and mutation metadata as needed.
- Preserve compatibility for callers that still produce legacy `subtasks`.
- Add strict Pydantic validation for:
  - unique phase IDs;
  - acyclic dependencies;
  - references only to known phase IDs;
  - valid phase statuses;
  - no mutation of immutable completed history;
  - valid terminal decisions.
- Add a structured `PlanMutation` / `SessionPlanMutation` model.
- Extend `evaluate_session_trajectory()` and `evaluate_session_trajectory_async()` to receive bounded session-plan context and return:
  - keep;
  - adjust;
  - skip;
  - replace;
  - append;
  - end;
  rather than only an escalation verdict.
- Retain `EscalationVerdict` compatibility where needed during migration.

#### Why

The planner is the canonical owner of plan schema and structured SLM output validation. Session adaptation cannot be reliable if mutations are represented only as free-form rationale text.

#### Behavioral contract

Invalid planner output, schema validation errors, unavailable SLMs, or malformed mutation JSON must result in no plan mutation and direct dispatch behavior. They must not become client-visible server errors.

---

### 8.2 `server/server_router.py`

#### Changes

- Replace the minimal `_session_replan_state` entries with a bounded session-supervision state that contains:
  - active plan reference;
  - plan revision;
  - compact ledger;
  - last observed turn metadata;
  - heartbeat generation/revision token;
  - replan pending state;
  - last mutation outcome;
  - timestamps needed for bounded lifecycle management.
- Keep `_get_session_key()` as the session correlation boundary, while making clear that fallback hash-based keys have weaker continuity guarantees.
- Promote `_run_async_slm_heartbeat()` to:
  - snapshot session state;
  - call asynchronous session trajectory evaluation;
  - validate and atomically apply a mutation;
  - mark the new plan revision ready for next eligible handoff.
- Add revision-aware application so stale asynchronous heartbeat results cannot overwrite a newer plan.
- On an eligible non-tool-loop request, prefer the active session plan over building a new dynamic DAG.
- When no active plan exists, create one through the existing slow planning path.
- On a terminal active plan, avoid injecting stale implementation work. Allow normal direct dispatch or a concise terminal context as appropriate.
- Record safe observability metadata for plan revisions and mutations.

#### Why

The router already owns session-key derivation, heartbeat scheduling, and the choice between direct and orchestration paths. It is the appropriate location for session-plan lifecycle coordination.

#### Behavioral contract

- Active healthy tool loops remain `DIRECT_ACTIVE_TIER`.
- `Turn Guard` behavior is unchanged.
- Heartbeat work remains asynchronous.
- A heartbeat cannot block request dispatch.
- Any state, SLM, config, or persistence failure degrades to direct dispatch.
- No change may introduce model calls, I/O, or asynchronous work into the routing selection hot path.

---

### 8.3 `orchestrator/handoff.py`

#### Changes

- Evolve `format_execution_handoff()` to accept a session plan and ledger rather than only analyst findings.
- Emit the versioned structured phase block described in this document.
- Render:
  - current decision;
  - plan ID and revision;
  - ready phases;
  - phase statuses;
  - dependencies;
  - `parallel_group`;
  - `parallel_to`;
  - post-conditions;
  - verification instructions;
  - compact evidence ledger;
  - explicit harness-execution authority.
- Preserve a concise prose rendering around the structured block for backward compatibility.
- Keep `ExecutionHandoff` as a string-compatible type where existing response paths expect it.
- Avoid generating provider-specific tool calls as part of this contract.

#### Why

The handoff is the only reliable cross-harness control surface. It must carry executable work structure, not merely a one-time implementation memo.

#### Behavioral contract

Every handoff must clearly state that parallelism is a harness-executed hint. The formatter must never claim that AutoConduck has executed, edited, or verified work it did not perform.

---

### 8.4 `orchestrator/dynamic_factory.py`

#### Changes

- Stop treating the per-turn DAG as the durable execution coordinator.
- Restrict the dynamic graph to optional bounded planning-time services:
  - optional RAG;
  - optional read-only reconnaissance;
  - plan synthesis.
- Ensure graph output can initialize a session plan but does not imply that graph nodes are execution phases.
- Remove or avoid any future wiring that turns implementation-phase nodes into AutoConduck-owned writer, shell, or verifier workers.
- If legacy DAG parallelism remains for read-only reconnaissance, label it distinctly from harness execution parallelism.

#### Why

Current DAG concurrency is useful only for research. Conflating it with real implementation fan-out caused the architecture mismatch this release corrects.

#### Behavioral contract

A dynamic graph can fail, be unavailable, or be disabled without preventing normal direct harness dispatch. It never owns actual code changes in v0.4.x.

---

### 8.5 `orchestrator/runner.py`

#### Changes

- Change `run_dynamic_orchestration()` from “build a fresh DAG for every slow turn” to:
  - initialize a plan only when no valid active session plan exists;
  - optionally refresh planning-time reconnaissance when a plan mutation explicitly requires it;
  - return the active or newly initialized session-plan handoff.
- Add plan revision awareness to runner inputs and outputs.
- Avoid graph rebuilding when an active plan can be handed off or revised from session state.
- Keep fail-soft fallback to direct routing if dynamic orchestration fails.

#### Why

The runner currently embodies the per-turn rebuild behavior. It must become an initialization/refresh mechanism rather than the primary execution lifecycle.

#### Behavioral contract

No runner failure may produce a 500. The fallback is direct dispatch without plan injection, not a partially malformed orchestration response.

---

### 8.6 `orchestrator/subagents.py`

#### Changes

- Preserve read-only analysis capabilities as optional bounded reconnaissance.
- Make the prompts and role semantics unambiguous:
  - `autoconduck_recon` is read-only;
  - it cannot edit files;
  - it cannot call harness tools;
  - it cannot claim test execution;
  - it cannot own a harness execution phase.
- Either map legacy `edit`, `verify`, and `bash` role labels to planning guidance only or deprecate those internal execution-suggestive labels in favor of clear reconnaissance roles.
- Return structured findings suitable for plan generation, including confidence and observed file references where available.
- Apply strict budgets using the existing `read_budget` concept.

#### Why

The existing labels imply powers the internal subagents do not possess. v0.4.x must make the boundary explicit to avoid accidental drift toward internal implementation workers.

#### Behavioral contract

Internal subagents remain optional and read-only. Their failure does not invalidate an otherwise usable harness plan.

---

### 8.7 `routing/model_pool.py` and `routing/dispatcher.py`

#### Changes

- Add only the minimum routing metadata required to distinguish:
  - initial plan creation;
  - optional reconnaissance;
  - asynchronous heartbeat evaluation;
  - final plan mutation or completion evaluation.
- Use existing capability, reasoning, context, tool, and price-cap selection semantics.
- Define explicit task-type or SLA requirements for heartbeat planning if needed, without changing the fit-gate-then-cheapest principle.
- Preserve `SelectionInfo` and `RoutingDecision` explainability for the new supervisor activity where practical.

#### Why

Heartbeat and plan-mutation calls need model selection, but v0.4.x must not turn model selection into a session I/O subsystem or a spend meter.

#### Behavioral contract

- Selection remains O(models), synchronous, in-memory, and sub-millisecond.
- No I/O, model call, session-store access, or asynchronous work is introduced inside selection.
- `max_price_usd_per_mtok` remains an opt-in per-selection price cap, not a session budget or time-based meter.
- Existing capability-floor behavior remains intact.
- C6 empirical scoring remains deferred and inert.

---

### 8.8 `harnesses/base.py`, `harnesses/claude_code.py`, `harnesses/opencode.py`, `harnesses/pi.py`, `harnesses/omp.py`

#### Changes

- Do not add harness-specific orchestration control channels.
- Confirm each harness adapter preserves the structured handoff as ordinary provider text rather than stripping or rewriting it.
- Preserve existing bounded configuration-edit behavior:
  - only between `# BEGIN AUTOCONDUCK` and `# END AUTOCONDUCK`;
  - backups remain in `~/.autoconduck/backups/`;
  - never modify config outside managed markers.
- Add compatibility documentation or tests showing that the same phase block reaches each harness through its existing provider integration.
- If a harness supports native delegation through its own normal agent behavior, document that it may interpret `parallel_group` and `parallel_to`; do not create bespoke transport logic in v0.4.x.

#### Why

Consistency belongs in the handoff contract, not in divergent harness-specific execution APIs.

#### Behavioral contract

All supported harnesses receive the same semantic contract. Different execution capabilities affect only how a harness consumes the contract, never the contract’s meaning.

---

### 8.9 Supporting observability and tests

The implementation will likely also require surgical changes to existing test modules and `/stats`-related paths where routing decisions are exposed.

Required observable fields should include, without storing excessive transcript content:

- session plan active/terminal state;
- plan ID and revision;
- heartbeat requested/completed/failed;
- mutation action;
- stale mutation rejection;
- current ready phases;
- terminal reason;
- fallback reason when supervision failed closed to direct dispatch.

No `/stats` field may be consumed by routing logic. `stats.py` remains write-only usage accounting with respect to routing decisions.

## 9. Explicit Non-Goals

v0.4.x will **not** build the following.

### 9.1 No synchronous puppet dance

AutoConduck will not implement a protocol of:

```text
AutoConduck emits one node
-> harness performs it
-> harness returns control
-> AutoConduck synchronously resumes graph
-> repeat for every node
```

This would add latency, create brittle state coupling, interfere with healthy harness tool loops, and incorrectly assume AutoConduck controls the external agent runtime.

### 9.2 No AutoConduck-owned implementation fan-out

AutoConduck will not create internal writer subagents that perform the real implementation fan-out. It will not add internal shell workers, code-editing workers, or test-running workers as the primary execution path.

Read-only internal reconnaissance may remain optional, bounded, and non-critical.

### 9.3 No harness-specific control channels

v0.4.x will not add:

- a Claude Code-specific remote worker API;
- an OpenCode-specific task dispatch channel;
- a Pi-specific agent-control protocol;
- provider-specific tool-call instructions masquerading as a universal API.

The shared message-level handoff contract is the compatibility boundary.

### 9.4 No changes to Turn Guard’s hot-path guarantees

`server/turn_guard.py` will remain:

- synchronous;
- I/O-free;
- regex-only;
- under the existing performance target;
- free of SLM, heartbeat, tool, or persistence calls.

Healthy multi-turn tool loops continue to route directly. v0.4.x must not reintroduce file-count or turn-count “complexity drift” escalation.

### 9.5 No reintroduction of complexity-drift escalation

The removed escalation behavior based on touching many files or reaching many turns remains removed. Healthy loops with many files or turns must not trigger replanning simply because they are long.

Only the existing genuine stagnation signals and the new evidence-driven session supervisor may justify plan mutation.

### 9.6 No C6 empirical scoring

v0.4.x will not build empirical success-weighted model scoring, `model_scores.json`, or usage-derived routing behavior. C6 remains deferred until real usage data supports it.

### 9.7 No mandatory persistent database in the first implementation step

Durable means durable across turns in the active session. v0.4.x may begin with bounded in-memory state and add a best-effort run-state snapshot only if it can satisfy fail-soft behavior. It will not make SQLite, LanceDB, or another optional native dependency mandatory for basic routing.

## 10. Implementation Ordering and Success Criteria

The implementation must be incremental. Each step must preserve a working direct-dispatch fallback.

### Step 1: Introduce the versioned session-plan model

**Work**

- Add plan ID, revision, phase schema, status model, ledger, terminal state, and mutation schema in `routing/slm_planner.py`.
- Add validation for dependency integrity, status transitions, and immutable history.

**Verification**

- Unit tests validate:
  - valid plans;
  - duplicate IDs;
  - dependency cycles;
  - invalid phase status transitions;
  - invalid mutation against a stale revision;
  - replacement and skip history retention;
  - terminal decision validation.

**Success criterion**

A plan can be created, serialized, mutated, and validated without invoking a LangGraph DAG or a harness.

---

### Step 2: Add session plan storage and asynchronous mutation application

**Work**

- Extend `server/server_router.py` session state.
- Promote `_run_async_slm_heartbeat()` to evaluate and apply validated phase mutations.
- Add compare-and-swap revision handling.
- Ensure all failures fall back safely to direct dispatch.

**Verification**

- Unit tests simulate:
  - heartbeat keep;
  - skip;
  - replace;
  - append;
  - end;
  - malformed SLM output;
  - SLM timeout/error;
  - stale heartbeat result after a newer revision;
  - missing session state.

**Success criterion**

For a multi-phase synthetic session, after evidence is recorded for phase 1, a heartbeat can mark phase 2 skipped or append a replacement phase. The next eligible handoff contains the new plan revision. A failed heartbeat leaves the previous plan untouched and request dispatch succeeds.

---

### Step 3: Emit the structured phase handoff contract

**Work**

- Evolve `orchestrator/handoff.py::format_execution_handoff()`.
- Render the canonical JSON-in-markdown phase block and concise prose instructions.
- Preserve string compatibility with existing server response paths.

**Verification**

- Snapshot tests verify:
  - initial plan handoff;
  - revised plan handoff;
  - terminal handoff;
  - malformed structured serialization fallback;
  - legacy prose readability.

**Success criterion**

A harness-visible message contains phase IDs, dependency order, `parallel_group`, `parallel_to`, post-conditions, verification instructions, status, and ledger without requiring a protocol-specific client.

---

### Step 4: Make the runner and dynamic graph plan-initialization-only

**Work**

- Modify `orchestrator/runner.py` and `orchestrator/dynamic_factory.py` so active session plans are reused rather than reconstructed every eligible turn.
- Retain optional bounded read-only reconnaissance for initial planning or explicit refreshes.
- Clarify `orchestrator/subagents.py` role semantics.

**Verification**

- Tests show:
  - first eligible turn creates a plan;
  - later eligible turns reuse the active plan;
  - graph reconstruction is not required for every turn;
  - internal reconnaissance failure still yields direct dispatch or a valid minimal plan;
  - no internal code-writing behavior is introduced.

**Success criterion**

An active plan spans multiple turns with a stable plan ID and increasing revision number. Graph construction occurs only for initialization or explicitly required planning refresh, not as a mandatory per-turn cycle.

---

### Step 5: Add post-condition-driven terminal decisions

**Work**

- Add final verification phase support.
- Teach heartbeat evaluation to emit `verify`, `end`, or follow-up phases based on evidence.
- Add terminal plan rendering.

**Verification**

- Tests cover:
  - successful verification leading to `end`;
  - missing verification retaining a verify phase;
  - failed verification appending corrective work;
  - a model claiming completion without evidence not ending the plan.

**Success criterion**

A task does not reach `end` merely because the implementation phase was attempted. It reaches `end` only after required post-conditions and verification evidence are recorded.

---

### Step 6: Add harness-facing parallelism annotations

**Work**

- Add `parallel_group` and `parallel_to` generation to planner output.
- Add validation that phases marked parallel have no direct dependency relationship.
- Ensure handoff instructions explicitly state that the harness chooses whether and how to fan out.

**Verification**

- Plan validation rejects incompatible parallel annotations.
- Handoff snapshots show parallel-ready phases.
- Integration tests confirm the same contract passes through Claude Code, OpenCode, and Pi adapter paths unchanged in semantic content.

**Success criterion**

For a plan with two independent phases, a parallel-capable harness receives an explicit fan-out opportunity. A sequential harness can execute the same plan in dependency-safe order without any special compatibility path.

---

### Step 7: Add observability and migration protection

**Work**

- Expose safe plan lifecycle and mutation metadata through existing observability paths.
- Add schema-version handling and migration behavior for active legacy sessions.
- Document in-memory lifecycle and any optional run-state persistence behavior.

**Verification**

- `/stats` or equivalent diagnostics show:
  - plan revision;
  - heartbeat outcome;
  - mutation action;
  - terminal state;
  - safe fallback reason.
- Legacy sessions without a v0.4 plan are initialized or direct-dispatched safely.

**Success criterion**

A multi-phase integration scenario is observable end-to-end:

1. The harness receives a phase contract.
2. The harness completes a phase and reports evidence.
3. The asynchronous heartbeat changes the remaining plan—such as skipping now-unneeded verification work or ending early after existing verification satisfies it.
4. The next handoff exposes the new revision and ledger.
5. The same structured phase contract flows cleanly through Claude Code, OpenCode, and Pi integrations.
6. Any planner or heartbeat failure degrades to direct dispatch without a 500.

## 11. Risks, Mitigations, and Open Questions

### 11.1 Opaque harness execution: how can phase completion be known?

**Risk:** AutoConduck does not directly observe filesystem state or execute tests. Harness messages may be incomplete, mistaken, or absent. A phase reported as complete may not actually satisfy its post-condition.

**Mitigation:**

- Treat harness statements as evidence, not proof.
- Prefer concrete evidence patterns:
  - changed file references;
  - tool output;
  - command results;
  - test results;
  - explicit unresolved failures.
- Require final verification phases for work where correctness matters.
- Use confidence-aware supervisor decisions:
  - low confidence means retain or append verification;
  - never issue `END` on unsupported completion assertions.
- Clearly distinguish `completed` from “issued to harness” and, where useful, distinguish evidence quality in ledger metadata.

**Open question:** The first schema should decide whether to model evidence confidence explicitly, for example `evidence_strength: reported | observed_tool_output | verified`. This is valuable but should not delay the basic phase lifecycle.

---

### 11.2 Harness may ignore parallelism hints

**Risk:** A harness may execute all phases sequentially, ignore `parallel_group`, or lack native multi-agent support.

**Mitigation:**

- Parallelism is advisory.
- Dependency correctness must not depend on concurrent execution.
- The structured contract remains executable sequentially.
- Success metrics must not assume every harness realizes speedup.
- Documentation should say “may fan out,” not “will fan out.”

**Decision:** This is acceptable. The value of v0.4.x is portable execution structure and session adaptation; native fan-out is an opportunistic harness capability.

---

### 11.3 Concurrent repository mutation can be unsafe

**Risk:** A planner may incorrectly identify phases as independent, causing a parallel-capable harness to run conflicting changes concurrently.

**Mitigation:**

- Parallel annotations require no dependency edge and non-overlapping expected mutation scopes where known.
- Default to sequential unless independence is clear.
- Use `parallel_group` only for genuine separable work.
- The harness remains responsible for its own worktree, merge, lock, and tool-concurrency policies.
- Do not encode “parallel” merely to maximize apparent agent activity.

**Open question:** Future versions may support an explicit `parallel_safety` field, such as `read_only`, `isolated_files`, or `requires_worktree`, but v0.4.x should avoid overdesigning a harness control protocol.

---

### 11.4 Heartbeat latency and multi-node cost

**Risk:** Asynchronous SLM evaluation can lag behind harness progress, consume model capacity, or produce stale advice.

**Mitigation:**

- Keep heartbeat asynchronous and bounded.
- Apply revision-aware compare-and-swap semantics.
- Coalesce pending heartbeat work per session rather than starting unbounded concurrent evaluations.
- Use existing model selection and price-cap semantics; do not add a session spend meter.
- Do not block direct dispatch or healthy tool loops while waiting.
- Prefer compact ledger and recent trajectory summaries over full transcripts.

**Decision:** Eventual plan adaptation is preferable to synchronous orchestration latency.

---

### 11.5 Session persistence beyond process memory

**Risk:** `_session_replan_state` is in memory. Restarting AutoConduck loses active plan state, and hash-derived session keys may be unstable.

**Mitigation:**

- v0.4.x must operate correctly if session state disappears: the next request either initializes a new plan or direct-dispatches.
- Do not make optional native persistence dependencies mandatory.
- Consider best-effort JSON snapshots in `~/.autoconduck/run/` with:
  - bounded retention;
  - atomic write/replace;
  - schema version;
  - redaction/minimization of sensitive message content;
  - failure ignored in favor of direct dispatch.
- Prefer explicit `x-session-id` or `x-thread-id` when harnesses provide them.

**Open question:** Whether restart continuity is required for v0.4.x or deferred to a later patch/minor release should be decided before implementation. The initial implementation must not claim durable-across-restart behavior unless it is actually provided.

---

### 11.6 Mutation or JSON parse failure

**Risk:** The SLM may return malformed structured output, contradictory dependencies, invalid statuses, or a mutation that violates plan history.

**Mitigation:**

- Validate every plan and mutation with strict typed models.
- Reject invalid mutation atomically.
- Retain the prior valid revision.
- Log safe diagnostics and expose a fallback reason where appropriate.
- Continue direct dispatch; never surface a 500.
- Never send malformed structured instructions to the harness as authoritative execution guidance.

**Decision:** Failure mode is “no adaptation,” not “broken session.”

---

### 11.7 Version and schema compatibility

**Risk:** Existing sessions, test fixtures, integrations, and old handoff consumers expect the current prose plan shape.

**Mitigation:**

- Add `schema_version` to all structured contracts.
- Preserve prose instructions around the structured payload.
- Support legacy `ExecutionPlan.subtasks` during migration or provide a deterministic conversion.
- Treat unknown schema major versions as non-executable structured content and fall back to prose/direct dispatch.
- Initialize active legacy sessions as v0.4 plans only when conversion is safe; otherwise start a new plan revision.

**Decision:** Schema compatibility is mandatory because the handoff is the cross-harness contract.

---

### 11.8 Plan drift and user intent changes

**Risk:** A user may change requirements mid-session. Blindly preserving the old plan can cause the harness to continue obsolete work.

**Mitigation:**

- Heartbeat treats clear new user intent as a potential `superseded` decision or a plan replacement trigger.
- Preserve old plan and ledger history for diagnostics.
- Do not silently merge materially incompatible objectives into the existing plan.
- Require the next handoff to state why the plan changed.

**Open question:** The exact threshold for “new request supersedes current plan” should be specified with examples during implementation, but it must not rely on file-count or turn-count heuristics.

---

### 11.9 Safety and privacy of session state

**Risk:** Persisting message trajectories or plan evidence may retain source-code or user-sensitive content.

**Mitigation:**

- Keep session snapshots bounded and minimal.
- Store phase summaries and evidence references rather than full transcripts when possible.
- Follow existing user-data location conventions under `~/.autoconduck/`.
- Ensure failure to write state never blocks routing.
- Document retention and cleanup behavior before enabling persistent snapshots by default.

---

## 12. Final Architectural Position

v0.4.x does not make AutoConduck a second coding agent that competes with Claude Code, OpenCode, or Pi. It makes AutoConduck a session-level supervisory router:

- It plans work as durable phases.
- It communicates executable structure to the real executor.
- It proposes safe parallelism but does not impersonate the harness’s worker runtime.
- It observes progress asynchronously.
- It revises only remaining work.
- It requires post-condition evidence before declaring completion.
- It preserves direct dispatch as the universal fail-soft path.

The harness owns tools, edits, verification execution, and native fan-out. AutoConduck owns model-aware planning, session memory, adaptation, and termination decisions. This division matches the actual provider architecture, preserves existing performance invariants, and creates a portable path to multi-agent execution benefits without introducing a brittle cross-harness control plane.
